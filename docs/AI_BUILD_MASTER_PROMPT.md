## 0. บทบาทและเป้าหมาย

คุณคือทีมพัฒนาซอฟต์แวร์เต็มรูปแบบ ประกอบด้วย Product Engineer, UX/UI Designer, Frontend Engineer, Backend Engineer, Database Engineer, Security Engineer และ QA Engineer หน้าที่ของคุณคือทำให้โปรเจกต์นี้กลายเป็นเว็บแอปจัดการชีวิตประจำวัน สุขภาพ การออกกำลังกาย โภชนาการ และการใช้เวลาที่ใช้งานได้จริง

**เป้าหมายไม่ใช่การสร้างเพียงหน้าตาเว็บหรือ mockup** แต่ต้องพัฒนาความสามารถที่ผู้ใช้กดใช้งานได้จริง มีการตรวจสอบข้อมูล มีการบันทึกและเรียกคืนข้อมูล มีการคำนวณที่ถูกต้อง มีสถานะ loading/error/success และมีการทดสอบ

อ่าน `docs/LIFE_HEALTH_PLANNER.md` ให้ครบก่อนเริ่มงาน เอกสารดังกล่าวเป็น Product & Technical Specification หลัก หากคำสั่งนี้กับไฟล์ดังกล่าวขัดกัน ให้:
1. รักษาข้อกำหนดด้านความปลอดภัยและความเป็นส่วนตัวในเอกสารไว้เสมอ
2. ใช้ความต้องการที่ผู้ใช้ระบุล่าสุดเป็นตัวตัดสินในเรื่องผลิตภัณฑ์
3. ห้ามเดาหรือสร้างข้อกำหนดที่มีผลต่อข้อมูลจริงขึ้นเอง ให้บันทึกเป็นคำถามหรือสมมติฐานที่ต้องยืนยัน
4. อัปเดตเอกสาร MD เมื่อข้อกำหนดหรือสถานะการพัฒนาเปลี่ยน

## 1. กฎการทำงานที่ห้ามละเมิด

1. **ตรวจสอบก่อนแก้:** สำรวจไฟล์ โครงสร้างโครงการ dependencies scripts และพฤติกรรมเดิมก่อนเขียนโค้ด ห้ามสมมติว่าโค้ดปัจจุบันทำงานอย่างไรโดยไม่ตรวจ
2. **รักษาสิ่งที่ทำงานอยู่:** เปลี่ยนเฉพาะส่วนที่จำเป็น ห้ามลบหรือเขียนทับความสามารถเดิมโดยไม่มีเหตุผลและการอนุมัติ
3. **ห้าม rewrite โดยไม่จำเป็น:** โปรเจกต์ปัจจุบันเป็น Node.js + Express + HTML/CSS/JavaScript แบบเรียบง่าย ให้คงสถาปัตยกรรมนี้ไว้ก่อน เว้นแต่มีเหตุผลทางเทคนิคที่พิสูจน์ได้และเสนอให้ผู้ใช้อนุมัติก่อน
4. **ทำงานเป็นช่วงเล็ก:** วางแผน แบ่ง milestone พัฒนา ทดสอบ และรายงานผลทีละช่วง อย่าทำการเปลี่ยนแปลงขนาดใหญ่โดยไม่ตรวจสอบระหว่างทาง
5. **ห้ามแสดงปุ่มหลอก:** ทุกปุ่ม เมนู ฟอร์ม ตัวกรอง กราฟ และ action ที่แสดงต้องทำงานจริง หากยังไม่รองรับให้แสดงสถานะ disabled/coming soon อย่างชัดเจน ไม่สร้างการตอบสนองปลอม
6. **ห้ามกล่าวอ้างเกินจริง:** ห้ามบอกว่าเชื่อมฐานข้อมูล สำรองข้อมูล ซิงก์หลายอุปกรณ์ ทดสอบผ่าน หรือ deploy แล้ว หากยังไม่ได้ทำและตรวจสอบจริง
7. **ไม่สร้างค่า/ข้อมูลปลอมปะปนข้อมูลจริง:** ข้อมูลตัวอย่างต้องแยกจากข้อมูลผู้ใช้ชัดเจน และมีทางลบหรือ reset ได้
8. **ไม่ฝัง secrets:** ห้ามใส่ API key, service-role key, password หรือ credential ลงใน source code, client bundle, Git history หรือ `NEXT_PUBLIC_*` variables
9. **ไม่ใช้บริการเสียเงินโดยปริยาย:** ใช้แนวทาง free-first ห้ามเปิดใช้ paid API, subscription, paid database หรือ AI provider ที่คิดเงินโดยไม่ได้รับอนุญาต
10. **ไม่ส่งข้อมูลสุขภาพออกนอกระบบโดยไม่ยินยอม:** AI ภายนอกเป็น optional เท่านั้น ต้อง opt-in อธิบายผู้ให้บริการและข้อมูลที่จะส่ง และส่งเท่าที่จำเป็น
11. **รองรับภาษาไทยและมือถือ:** UI หลักเป็นภาษาไทย ใช้ได้บน desktop, tablet และ mobile พร้อม keyboard accessibility
12. **จัดการเวลาอย่างถูกต้อง:** ใช้ timezone ของผู้ใช้ (ค่าเริ่มต้น `Asia/Bangkok`) และแยก date-only ออกจาก timestamp
13. **อัปเดตเอกสาร:** บันทึกสิ่งที่ทำแล้ว สิ่งที่ยังไม่ทำ ข้อจำกัด วิธีรัน และวิธีทดสอบใน `docs/LIFE_HEALTH_PLANNER.md`
14. **ห้ามหยุดแค่เสนอแผน:** เมื่อมีสิทธิ์แก้ repository ให้ลงมือทำ milestone ที่ได้รับมอบหมายจริง แต่หากขาด credential หรือการอนุมัติที่จำเป็น ให้ทำส่วนที่ทำได้โดยไม่ใช้ credential นั้น แล้วแจ้งสิ่งที่ต้องการอย่างชัดเจน

## 3. ภาพรวมผลิตภัณฑ์และหน้าหลัก

สร้างเว็บแอปแบบ personal dashboard มีเมนูหลักอย่างน้อยดังนี้:

1. **ภาพรวม (Overview):** สรุปข้อมูลวันนี้ งานตามแผนเทียบกับเวลาจริง โภชนาการ การออกกำลังกาย การนอน และตัวชี้วัดที่บันทึกไว้
2. **ตารางชีวิต (Schedule):** ตารางกิจกรรมรายวัน/รายสัปดาห์ แก้ไข เพิ่ม ลบ ย้าย ทำซ้ำ และปรับตารางได้
3. **บันทึกเวลาจริง (Time Log):** บันทึกว่าใช้เวลาทำอะไรจริง เมื่อใด นานเท่าใด
4. **ออกกำลังกาย (Exercise):** แผนรายวัน/รายสัปดาห์ วิธีทำ ท่าฝึก เซ็ต/ครั้ง/เวลาพัก การบันทึกผล และการปรับแผนอย่างมีหลักฐาน
5. **โภชนาการ (Nutrition):** บันทึกมื้ออาหาร ปริมาณ และสารอาหาร พร้อมยอดรวมเทียบเป้าหมาย
6. **ข้อมูลร่างกาย (Body Metrics):** บันทึกค่าที่ผู้ใช้เลือก เช่น น้ำหนัก ส่วนสูง รอบเอว ระยะเวลานอน และปริมาณน้ำ
7. **รายงาน (Reports):** วิเคราะห์รายวัน รายสัปดาห์ รายเดือน รายปี และช่วงวันที่กำหนดเอง
8. **ตั้งค่า (Settings):** เวลาเริ่มต้น/สิ้นสุดวัน timezone เป้าหมาย หน่วย หมวดหมู่ และการจัดการข้อมูลส่วนบุคคล

ทุกหน้าต้องมี navigation ที่ชัดเจน มีสถานะหน้าปัจจุบัน และใช้งานได้จริงทั้งจอเล็กและจอใหญ่

## 4. ตารางชีวิตและการจัดการกิจกรรม

ผู้ใช้ต้องควบคุมตารางได้เองทั้งหมด ค่าเริ่มต้นเป็นเพียง template ที่แก้ไขได้ ไม่ใช่ข้อบังคับ

ค่าเริ่มต้นตัวอย่าง:
- ตื่น 06:30
- กลับถึงบ้านโดยประมาณ 18:00
- ซื้ออาหาร/มื้อเย็น 18:00–18:40
- อาบน้ำและพัก 18:40–19:20
- ออกกำลังกายหรือฟื้นตัว 19:20–20:10
- เรียน/ศึกษาด้วยตนเอง 20:20–21:05
- เล่นเกม/เวลาส่วนตัว 21:05–21:50
- เตรียมตัวนอน 21:50–22:00
- เข้านอน 22:00

ข้อกำหนด:
- เพิ่ม แก้ไข ลบ ทำสำเนา ย้ายวัน และเปลี่ยนลำดับกิจกรรมได้
- กำหนดชื่อ หมวดหมู่ วัน วันที่ เวลาเริ่ม เวลาสิ้นสุด สถานที่/หมายเหตุ และสถานะ
- ใช้ input เวลาแบบ structured time ไม่ใช้ข้อความอิสระเป็นแหล่งข้อมูลหลัก
- รองรับกิจกรรมครั้งเดียวและกิจกรรมประจำสัปดาห์ พร้อมแก้เฉพาะครั้งนี้หรือทั้งชุด
- ตรวจเวลาสิ้นสุดก่อนเวลาเริ่มต้น และป้องกัน duration ติดลบหรือเป็นศูนย์เมื่อไม่อนุญาต
- ตรวจจับเวลาทับซ้อน แจ้งชื่อกิจกรรมและช่วงเวลาที่ชนกัน ให้ผู้ใช้เลือกแก้หรือยืนยันกรณีตั้งใจซ้อน
- สถานะอย่างน้อย: planned, completed, skipped, rescheduled
- การแก้ template หรือคำแนะนำต้องไม่เขียนทับกิจกรรมที่ผู้ใช้ปรับเองโดยไม่ยืนยัน
- อนุญาตกิจกรรมนอกตารางปกติ วันหยุด และตารางที่เปลี่ยนแปลงเฉพาะวัน
- เปรียบเทียบระยะเวลาที่วางแผนกับเวลาที่ทำจริง และแสดงส่วนต่างอย่างเข้าใจง่าย

## 5. การบันทึกเวลาที่ใช้จริง

บันทึกได้หลาย session ต่อกิจกรรมต่อวัน โดยมี:
- วันที่
- กิจกรรมและหมวดหมู่ (งาน เรียน ออกกำลังกาย พักผ่อน ชีวิตประจำวัน เดินทาง และหมวดหมู่กำหนดเอง)
- เวลาเริ่ม/สิ้นสุด หรือระยะเวลา
- หมายเหตุ
- แหล่งที่มา/กิจกรรมตามแผนที่เกี่ยวข้อง (ถ้ามี)

กฎการคำนวณ:
- คำนวณเวลาจากค่าตัวเลข เช่น integer seconds/minutes ไม่คำนวณจากข้อความที่จัดรูปแบบแล้ว
- ตรวจ start/end และข้ามวันให้ถูกต้อง
- ตรวจ session ที่ทับซ้อนและเตือนก่อนบันทึกหรือก่อนรวมยอด
- ห้ามนับช่วงเวลาที่ทับซ้อนซ้ำโดยไม่แจ้ง
- แสดง planned vs actual, เวลาที่ไม่ถูกจัดหมวดหมู่ และความครบถ้วนของข้อมูล
- รวมยอดตามวัน สัปดาห์ เดือน ปี หมวดหมู่ และ custom date range
- แก้ไขและลบรายการย้อนหลังได้ โดยรายงานต้องคำนวณใหม่จากข้อมูลต้นทาง

## 6. ระบบออกกำลังกาย

ระบบต้องเป็นมากกว่ารายการท่าออกกำลังกาย:
- แผนฝึกแยกวันฝึก วันพัก และวันฟื้นตัว
- แต่ละท่ามีชื่อ คำอธิบาย วิธีทำทีละขั้น จุดที่ควรระวัง กล้ามเนื้อเป้าหมาย ระดับความยาก อุปกรณ์ที่ต้องใช้ และทางเลือกที่เหมาะสม
- แสดง sets, reps หรือ duration, rest interval, tempo (ถ้ามี), และเป้าหมายของท่า
- บันทึกผลจริงแต่ละ session ได้แก่ เซ็ต จำนวนครั้ง ระยะเวลา ความยากที่รับรู้ (RPE/RIR หากใช้) และหมายเหตุอาการไม่สบาย
- เก็บ version ของแผนเพื่อย้อนดูว่าใช้แผนใดในวันที่ฝึก
- แสดงความสม่ำเสมอ ปริมาณการฝึก และแนวโน้ม performance
- เปลี่ยนท่าหรือเพิ่มความยากเมื่อข้อมูลการทำจริงและการฟื้นตัวรองรับเท่านั้น ไม่สุ่มเปลี่ยนท่าทุกสัปดาห์
- ใช้ progressive overload แบบค่อยเป็นค่อยไป พร้อมอธิบายเหตุผลและเงื่อนไข
- หากทำไม่ครบ เหนื่อยมาก นอนน้อย หรือมีอาการเจ็บ ให้คงระดับ ลดระดับ หรือเสนอพัก แทนการเพิ่มความหนักอัตโนมัติ
- ให้ผู้ใช้ยืนยันก่อนนำแผนใหม่มาแทนแผนเดิม
- มีคำเตือนให้หยุดเมื่อเจ็บแปลบ เวียนศีรษะ เจ็บข้อ หรือมีอาการผิดปกติ และขอคำแนะนำจากผู้เชี่ยวชาญเมื่อเหมาะสม
- ห้ามวินิจฉัยอาการบาดเจ็บหรือให้คำแนะนำแทนแพทย์

## 7. ระบบอาหารและโภชนาการ

ให้บันทึก:
- วันที่/เวลา มื้ออาหาร ประเภทอาหาร ชื่ออาหาร ปริมาณ/หน่วยบริโภค
- พลังงาน kcal, โปรตีน, คาร์โบไฮเดรต, ไขมัน และข้อมูลเสริมที่มีแหล่งข้อมูลรองรับ
- แหล่งที่มาของค่าทางโภชนาการ เช่น ผู้ใช้กรอก ฐานข้อมูลนำเข้า หรือค่าประมาณ
- ระดับความมั่นใจ/สถานะ estimated, imported, user-confirmed

ความสามารถ:
- เพิ่ม แก้ไข ลบ และคัดลอกมื้ออาหาร
- ตั้งเป้าหมายรายวันได้เองและแก้ไขภายหลัง
- รวมยอดรายมื้อและรายวัน พร้อมแสดงพลังงานและ macro ที่เหลือเมื่อเทียบเป้าหมาย
- แสดงกราฟแนวโน้มและค่าเฉลี่ยตามช่วงเวลา
- วิเคราะห์ช่องว่างของสารอาหารและเสนออาหารที่ช่วยเติมส่วนที่ขาด โดยคำนึงถึงข้อจำกัดอาหารที่ผู้ใช้ระบุ
- ผู้ใช้แก้ไขค่าที่ระบบแนะนำหรือนำเข้าได้
- หากไม่ทราบปริมาณหรือสูตรอาหาร ห้ามแสดงตัวเลขแม่นยำเกินจริง ให้ระบุว่าเป็นค่าประมาณหรือขอข้อมูลเพิ่ม
- ห้ามบังคับลดแคลอรีหรือแนะนำการอดอาหาร/การกินแบบสุดโต่ง
- ไม่จำเป็นต้องเชื่อม API อาหารในระยะแรก หากยังไม่มีแหล่งข้อมูลฟรีที่ตรวจสอบได้ ให้รองรับการกรอกเองก่อน

## 8. ข้อมูลร่างกายและการพักผ่อน

- บันทึกข้อมูลแบบมีวันที่และหน่วยชัดเจน เช่น น้ำหนัก kg ส่วนสูง cm รอบเอว cm เวลานอน ชั่วโมง ปริมาณน้ำ ml และตัวชี้วัดกำหนดเอง
- เพิ่ม แก้ไข ลบ และดูประวัติย้อนหลังได้
- แสดงกราฟแนวโน้มโดยไม่สร้างค่าที่ไม่มีการบันทึก
- คำนวณ BMI เฉพาะเมื่อส่วนสูงและน้ำหนักถูกต้อง พร้อมระบุชัดว่าเป็นเพียง screening metric ไม่ใช่การวินิจฉัย
- ห้ามคาดเดาเปอร์เซ็นต์ไขมันหรือมวลกล้ามเนื้อโดยไม่มีแหล่งวัดที่เหมาะสม
- ข้อมูลสุขภาพและบันทึกส่วนตัวเป็นข้อมูลอ่อนไหว ต้องไม่เปิดเผยใน URL หรือ log ที่ไม่จำเป็น
- ฟิลด์ที่ไม่จำเป็นต้องเป็น optional จริง ๆ

## 9. รายงานและ Dashboard

ตัวกรอง:
- วันนี้/วัน
- สัปดาห์
- เดือน
- ปี
- ช่วงวันที่กำหนดเอง

รายงานต้องคำนวณจากวันที่จริง ไม่ใช่เพียงเปลี่ยนชื่อหัวข้อหรือใช้ข้อมูลตัวอย่างเดิม:
- เวลารวมแยกตามหมวดหมู่และกิจกรรม
- planned vs actual และความแตกต่าง
- เวลาทับซ้อน/เวลาที่ยังไม่จัดหมวดหมู่
- โภชนาการ: kcal, protein, carbohydrate, fat, ค่าเฉลี่ย และจำนวนวันที่มีข้อมูล
- การออกกำลังกาย: จำนวน session ความสม่ำเสมอ ปริมาณและ performance trend
- ข้อมูลร่างกาย: แนวโน้มจากค่าที่บันทึกจริง
- แสดงวันที่เริ่มและสิ้นสุดของช่วงรายงาน
- แสดงจำนวนวันที่มีข้อมูลและวันที่ข้อมูลขาดหาย
- กราฟต้องมี label, unit, tooltip/รายละเอียด และ empty state
- เมื่อแก้ไขหรือลบข้อมูลต้นทาง รายงานต้องสะท้อนข้อมูลใหม่
- ห้ามเติมวันที่ไม่มีข้อมูลด้วยเลขศูนย์โดยไม่อธิบาย เพราะอาจทำให้ค่าเฉลี่ยผิด
- ตรวจขอบเขต timezone, สัปดาห์ที่คร่อมเดือน/ปี, leap year และวันสุดท้ายของเดือน

## 10. ระบบวิเคราะห์และคำแนะนำ

เริ่มจาก deterministic rules engine ที่ตรวจสอบได้ ไม่ต้องพึ่ง AI API:
- วิเคราะห์ว่ากิจกรรมใดทำได้ตามแผนหรือคลาดเคลื่อนต่อเนื่อง
- หากเวลาเรียน/งานส่วนตัวต่ำกว่าแผนหลายวัน เสนอปรับ block ให้เล็กลงและทำได้จริง ไม่ตำหนิผู้ใช้
- หากสารอาหารต่ำกว่าเป้าหมาย ให้แสดงส่วนที่ขาดโดยอิงเฉพาะข้อมูลที่บันทึก และเสนออาหารเป็นตัวเลือก
- หาก performance และ recovery สนับสนุน จึงเสนอเพิ่มระดับการฝึกเล็กน้อย
- หากนอนน้อยต่อเนื่อง ให้เสนอปรับตารางโดยไม่ดึงเวลาจากการนอนเพิ่ม
- พิจารณาความครบถ้วนของข้อมูลก่อนให้คำแนะนำ

ทุกคำแนะนำต้องแสดง:
1. สิ่งที่สังเกตพบ
2. ช่วงวันที่ใช้วิเคราะห์
3. ข้อมูลจริงที่เป็นหลักฐาน
4. กฎ/เงื่อนไขที่ทำให้เกิดคำแนะนำ
5. ระดับความมั่นใจหรือข้อจำกัด
6. ขั้นตอนที่ผู้ใช้เลือกทำได้

ห้ามแต่งข้อมูล ห้ามกล่าวว่า AI วิเคราะห์ หากไม่ได้เรียก AI จริง และห้ามแสดงคำแนะนำที่อาศัยข้อมูลซึ่งผู้ใช้ไม่ได้บันทึก

## 11. สถาปัตยกรรมและการจัดเก็บข้อมูล

### ระยะเริ่มต้น
- คง Node.js + Express และโครงสร้างแอปปัจจุบัน
- ใช้ HTML/CSS/JavaScript ที่มีอยู่ก่อน
- ใช้ localStorage ได้เฉพาะ prototype หรือ offline-first ระยะเริ่มต้น พร้อมเตือนว่าข้อมูลอยู่ใน browser/device เดียวและอาจหายเมื่อเคลียร์ข้อมูล
- แยก data access layer และ business logic ออกจาก UI ให้เปลี่ยน backend ได้โดยไม่ต้องเขียนหน้าจอใหม่ทั้งหมด
- ทำ schema versioning และ migration สำหรับข้อมูล localStorage
- มี export/import ข้อมูลเป็น JSON พร้อม validation และยืนยันก่อนเขียนทับ

### ระยะ Cloud (ยังไม่อนุญาตให้สมมติว่าเชื่อมแล้ว)
Supabase Free เป็นเพียงตัวเลือกที่แนะนำ ไม่ใช่การเชื่อมต่อที่ได้รับอนุญาตโดยอัตโนมัติ ก่อนเริ่ม:
- ต้องมี Supabase project และ credentials ที่เจ้าของโปรเจกต์อนุญาตให้ใช้
- ตรวจสอบ quota, inactivity/pause policy, backup limitations, region และเงื่อนไขล่าสุดจากเอกสารทางการ
- ถ้ายังไม่มี credentials ให้ทำ migration/schema draft และ adapter interface ได้ แต่ห้ามอ้างว่า cloud persistence ทำงานแล้ว
- ใช้ตารางตามข้อกำหนดใน MD: profiles, activities, time_logs, exercise_plans, exercise_sessions, food_entries, body_measurements และ daily_summaries เมื่อจำเป็น
- ทุกตารางข้อมูลส่วนบุคคลต้องมี owner/user ID ที่อ้างอิง auth user
- เปิด RLS ทุกตาราง และเขียน SELECT/INSERT/UPDATE/DELETE policies ที่จำกัดเจ้าของข้อมูล
- ทดสอบ cross-user isolation ด้วยผู้ใช้มากกว่าหนึ่งบัญชี
- ห้ามใช้ public/anonymous read policies กับข้อมูลสุขภาพ/กิจวัตร
- ห้ามเปิดเผย service-role key ใน browser หรือ client bundle
- ทำ export และ permanent delete-my-data flow
- เก็บ timestamp เป็น UTC พร้อม timezone IANA ของผู้ใช้ และเก็บ date-only แยกต่างหาก

## 12. ความปลอดภัย ความเป็นส่วนตัว และความน่าเชื่อถือ

- เก็บข้อมูลเท่าที่จำเป็น ใช้ validation ทั้ง client และ server
- ป้องกัน XSS โดย escape ข้อมูลผู้ใช้ ห้ามแทรก user input เป็น raw HTML
- ป้องกัน injection, mass assignment และการเข้าถึง record ของผู้ใช้อื่น
- ใช้ secure headers และตั้งค่า Express ให้เหมาะสม
- ไม่บันทึก health notes หรือข้อมูลส่วนตัวลง application logs
- หากเพิ่ม authentication ต้องใช้ session/cookie configuration ที่ปลอดภัย และไม่สร้างระบบ auth แบบทำเองโดยไม่มีเหตุผล
- แสดง privacy notice ที่เข้าใจง่าย ระบุว่าข้อมูลเก็บที่ใดและลบ/ส่งออกอย่างไร
- มี confirm dialog สำหรับการลบหรือ import ที่เขียนทับข้อมูล
- จัดการข้อผิดพลาดโดยไม่เปิดเผย stack trace หรือ secrets ให้ผู้ใช้
- ทำ graceful handling เมื่อ backend หรือ AI provider ใช้งานไม่ได้

## Evidence-based workout coach requirements

When modifying the Gemini workout coach:

- Keep the Gemini Free Tier unless the user explicitly approves a different cost model. Do not introduce paid search, vector database, or third-party subscriptions.
- Use the reviewed, versioned server-side catalog at `data/exercise-evidence.json`; do not let the model invent source titles, years, DOI values, URLs, or exercise IDs.
- Separate programming-level evidence from exercise-specific technique guidance. Never imply that an umbrella review tested a particular movement when it only supports resistance-training principles.
- Resolve all visible citation metadata and URLs from the local trusted catalog on the server. Display the rationale for each exercise and clickable citations in the UI.
- Constrain model exercise selection to approved catalog IDs. If no appropriate movement exists, disclose the gap or ask a question rather than inventing an exercise.
- Preserve known catalog limitations, including lack of sufficiently loaded pulling movements when no equipment is available.
- Treat the evidence library as a curated snapshot, not live literature retrieval. Include review dates, evidence scope, and limitations; update it only from authoritative sources.
- Validate the returned exercise IDs and evidence IDs server-side before rendering or saving a plan. Ignore unknown IDs and model-provided citation URLs.
- Keep personal data minimization and opt-in sharing behavior intact. Never add unrelated nutrition or life-activity data to Gemini payloads.
